02 · The structure

Written in src/, bundled into two files

Everything is written by hand in a few files in src/. A runite turns them into exactly two: one static page for the browser and one PHP function for the API. Nothing else is deployed.

profile3/                   the project anwarachilles
├── cast                    runite · build · serve · watch · start · store · password
├── exura                   runite · install / remove the Exura series from the CDN
├── vercel                  runite · link · push · data · env (the Vercel CLI)
├── vercel.json             output public/, the routes, the PHP runtime
├── router.php              vercel.json, locally (php cast serve)
├── src/                    written by hand
│   ├── index.head.html     <head>: meta, fonts
│   ├── index.html          <body>: every <exura-*> template
│   ├── index.css           <style>: tokens and layout over ExuraCSS
│   ├── index.js            <script>: function → class → DOMContentLoaded
│   ├── index.php           the API: login, bio, career, item, schema, ai
│   └── exura/              exura.css · exura.js · exura.php
├── public/                 made by cast
│   └── index.html          head + exura + src, one file
└── api/                    made by cast
    └── index.php           exura.php + src/index.php, one function
03 · Rune

A concept beneath PHP, carved into runites

Rune is not a framework that dictates the work: it responds to it. It is a lore-driven, modular concept beneath PHP, where every rune follows one paradigm, Ether · Essence · Entity · Manifest · Phantasm. An app carved with runes is a runite. This site carries three of them, each a single PHP file run from the terminal.

php cast build

Crafter bundles the shards of src/ into public/index.html and api/index.php; Keeper stores them; Specter runs serve and watch beside the flow.

php exura setup

Fetches ExuraCSS, ExuraJS and ExuraPHP of a chosen tag into src/exura/, so the build bundles them in. No package manager on the page, no node_modules.

php vercel push

Speaks to the Vercel CLI: link, push, data (the database URL) and env (the env, pulled into .env).

The origin runes used here: Aether, Chanter, Cipher, Crafter, Forger, Keeper, Specter, Weaver, Whisper.

04 · Reliquary

It started as a relic: build-vercel-app

Reliquary is the Relic Package Manager of Rune: a registry (relic.json, nexus.json) of runites that anyone can pull. This site began from one of them, build-vercel-app from rune-apps: a static page in public/, an ExuraPHP API in api/, a router.php that mirrors vercel.json, and the vercel runite. On top of that template came the pages, the dashboard, Neon and the AI.

05 · The Exura series

Three light pieces, one focus each

Exura mirrors what modern frameworks give, CSS, JavaScript and PHP, while staying super light. Each piece is judged by its own focus.

ExuraCSS

Style as attributes

Layout is written as meaning: flex="j:between a:middle", size="p:2", md:size="w:1/3". Dark mode is one attribute, <body dark>, and the colors balance themselves. This site adds its own tokens on top, and spaces blocks with padded wrappers, never gap.

ExuraJS

A module is a tag

Every <exura-*> in the HTML is one class. Exura.module(PagesNews) gives it dom, state, effect, render and router; static async start() wakes it, and it routes itself. The templates stay in the HTML, not in strings of JavaScript.

ExuraPHP

A route is a function

Exura::module('GET', 'career', fn): one route, one function, one JSON answer. The folder api/ drops off by itself, and anything unknown falls back to a 404 in JSON.

06 · Rune × Exura

Each works where the other does not

Rune lives before the deploy, in the terminal; Exura lives after it, in the browser and the function. Neither dictates the other, and that balance keeps the site small.

Before · the terminal

Rune shapes the files

  • bundles src/ into one page and one function
  • serves locally exactly like Vercel (router.php)
  • rebuilds on every change (watch)
  • keeps the password hash (php cast password)
  • ships to Vercel (php vercel push)
After · the visit

Exura runs the site

  • ExuraCSS lays out every page
  • ExuraJS wakes the module of the path
  • ExuraPHP answers /api/* as JSON
  • the dashboard writes through the same API
  • no framework runtime, no build step in the browser
07 · Vercel

A static page and one PHP function

Vercel serves public/ as files and runs api/index.php with the community runtime vercel-php. The routes are three lines, and the same file drives the local server.

{
  "outputDirectory": "public",
  "functions": { "api/*.php": { "runtime": "vercel-php@0.7.4", "includeFiles": "api/*.txt" } },
  "routes": [
    { "src": "/api/(.*)", "dest": "/api/index.php" },                 every API call: one function
    { "src": "/(profile|skill|…|dashboard)(/.*)?", "dest": "/index.html" }, every page: one file
    { "src": "/(.*)", "dest": "/$1" }                                 assets as they are
  ]
}

Secrets never sit in the code: DATABASE_URL, the key of the assistant and the hash of the login password, ADMIN_PASSWORD_HASH, are envs of Vercel, and a local .env that is never committed nor deployed.

08 · Neon

The memory: serverless Postgres

The filesystem of a Vercel function is read-only, so the content lives in Neon. The API speaks to it with PDO, and the schema heals itself: when Postgres says a table or a column is missing, the API creates it once and runs the query again. No migration step, no check before every query.

  • bioone row: name, alias, profession, domicile, birth
  • careertitle, company, months, duties, skills as ids
  • itemskill or follow: name, link, icon
09 · Routing & SEO

Every link is a real page load

There is no client router here. A link is a plain <a href="/profile">: the browser asks the server, Vercel answers the page with a 200, and on arrival every module checks the path. The one that matches renders itself; the others stay empty.

Real URLs

No #/ and no history tricks: every address can be shared, bookmarked and opened cold. Back and forward are the browser's own.

Friendly to crawlers

Each page answers as a document, with a canonical, Open Graph and a schema.org Person in the head. Search engines that run JavaScript see the page as visitors do.

A fresh start each time

A reload clears what the last page left in memory: no stale state, no listeners piling up. What carries over is chosen on purpose, in sessionStorage.

10 · Data

Asked once per tab, then remembered

Because every link reloads, the site would ask the API again and again. It does not: one small function, kept(key, load), reads a copy from sessionStorage when there is one, and only otherwise loads and keeps it. Rendering is just as careful: a module re-renders only when the state it shows changes, and a ticking clock patches its own text instead.

A save in the dashboard forgets the kept content, so the next page shows the change. The dashboard itself always asks the API, and sessionStorage ends with the tab.

11 · Ask AI

An assistant that reads the same data

The sparkle at the bottom right asks POST /api/ai. ExuraPHP adds the character of the assistant and the facts from Neon (bio, career, skills, links) to the question, and sends it to the language model behind the assistant. The key stays on the server; the conversation stays in the tab.

Small pieces, each doing one thing, made by one community.

Reliquary

PROJECT - FEDERATED RELIC REGISTRY

A home for the snapshots of Rune relics, without one central registry to trust or to keep alive. Every registry is a fork that holds its own list of relics and points to the others, so they reach each other peer to peer, as a federation.

  • a relic is a runite packed as one file (cast.rune)
  • a registry is a repository: relic.json lists its relics, nexus.json its peers
  • no central server: forks connect the registries to each other
  • next: every snapshot sealed by its hash, so a copy can be trusted from any peer
